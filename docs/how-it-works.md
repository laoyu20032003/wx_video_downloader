# 它是怎么工作的

本文记录微信 PC 4.2 视频号的变化、为什么旧方案失效，以及本项目的两条腿：**透明代理拿地址** + **进程内存取明文头**。

## 1. 微信 4.2 的视频号变了

在 4.0/4.1 时代，视频号是一个网页应用：页面来自 `channels.weixin.qq.com`，工具通过 MITM 改写 HTML、注入 `channels.ws.js` 和下载按钮，页面再通过本地 WebSocket 与下载器通信。

4.2 之后，视频号入口变成 **原生 liteapp**：

- 页面请求走 `liteapp.weixin.qq.com`，而且**不在网络层出现**——liteapp 是微信内置的，模板与数据由原生层（MMTLS）下发；
- 抓包只能看到视频分片（`finder.video.qq.com`）和少量上报（`channels.weixin.qq.com/web/report-perf?pf=lite`）；
- 全程没有携带 `decodeKey` 的 JSON。

结论：**没有网页可注入，密钥也不经过网络**。所有依赖“注入页面”或“抓 JSON 拿 key”的工具，在 4.2 上都会失效。

## 2. 视频本身的加密方式

请求视频时服务器会返回：

```
X-encflag: 1
X-enclen: 131072
```

含义是最前面的 **131072 字节（128 KiB）被加密**，其后是明文。加密使用 ISAAC64 流密钥，种子来自页面数据里的 `decodeKey`（≤20 位整数）。

因此，一个“没解密”的文件特征是：

- 文件大小正常、扩展名 mp4；
- 开头是随机字节，找不到 `ftyp` / `moov`；
- 但从偏移 131072 开始是正常的 H.264/H.265 长度前缀数据；
- 播放器打不开，`ffmpeg` 报大量 `Invalid NAL unit size`。

## 3. 本项目的做法

### 3.1 拿地址：透明代理

`mitmproxy` 以透明转发方式运行，只把 `qq.com` 的请求记录到 `flows.log`，不改写任何响应：

```
mitmdump -q -p 8898 --set confdir=mitm -s capture.py
```

系统代理指向 `127.0.0.1:8898`。

上游的判定必须严格，否则会直接毁掉可用性：注册表里的 `ProxyServer` 是个"上次写成什么就一直留着"的字段，即使 `ProxyEnable=0`（系统代理已关闭）它也可能残留着某个本机端口。早期版本无条件相信这个值，一旦那个端口没人监听（比如关了 v2rayN），mitmproxy 会把所有请求转给死端口，微信里满屏 `502 Bad Gateway / WinError 1225`。

现在的规则（`Resolve-Upstream`）：

1. `ProxyEnable` 不是 1 ⇒ 直连；
2. `ProxyServer` 不是 `127.0.0.1:<port>` / `localhost:<port>` ⇒ 直连；
3. 上游端口 == 本工具端口 ⇒ 直连（否则自己转发给自己，形成死循环）；
4. 对上游做一次 TCP 探测（800ms 超时），连不上 ⇒ 直连；
5. 全部通过 ⇒ 以 `--mode upstream:http://<上游>` 链式转发。

启动后还会用 `http://www.baidu.com/` 从代理自身走一发探针：若返回 502 说明上游其实不可用，就地杀掉重启为直连。这样"上游挂了"只会退化成直连，不会变成整页报错。

另一个坑在 `capture.py`：视频响应必须设 `flow.response.stream = True`。mitmproxy 的 `flow.response.content` 一旦被访问，整个响应体就会被缓冲进内存——一条几百 MB 的视频会让代理内存翻倍、播放明显变卡。所以媒体类 URL 只取状态码和地址，体积字段记 `-1`，body 原样透传。反过来说，如果哪天发现"只有视频播不动其它正常"，先检查这里。

### 3.2 拿明文头：读进程内存

微信播放视频时，会把解密后的前 131072 字节留在 `WeChatAppEx.exe` 的内存里。`MemScan.cs` 通过 `ReadProcessMemory` 扫描堆区，按 MP4 的 box 结构定位：

```
[4 字节 size][ftyp] ... [4 字节 size][moov]
```

即：某个位置 `+4` 是 ASCII `ftyp`，之后能撞上 `moov`（允许中间夹着 `free` / `uuid` 这类空 box，最多跨 3 个；只认紧挨着的那种会整条漏掉），两个 size 都在合理范围。命中后 dump 出 131072 字节，就是该视频的明文头。

### 3.3 拼接与校验

```
完整文件 = 内存明文头(131072) + 下载到的密文[131072:]
```

拼接后先 `ffprobe` 读时长，再 `ffmpeg` 解码前 3 秒；通过后做一次**全片解码**，0 错误才落到输出目录。

**为什么不能"只试第一个候选"**：内存里同时躺着好几条视频的头，扫描按地址顺序返回，第一个未必是本条视频的。实测三份不同视频的 128KB 头字节完全相同（同一 md5）；也见过 `moov` 只有 9KB 的头一次成功、`moov` 有 232KB 的头被判坏——差别不在 moov 大小，而在"它是不是这条视频的"。所以：

1. 去重键用**整段头的 MD5**，不是前 64 字节；
2. 每个候选先过**结构闸门**（见 3.4），不再拿解码试错；
3. 每个候选的拼接 / ffprobe / ffmpeg 各自 `try/catch` 隔离，一个候选失败只跳过它；早期版本一条报错就把整条视频判死，这才是"只成功过一个"的直接原因。

### 3.4 怎么认出「这条视频」

`flows.log` 里 `stodownload` 的请求分两类：

- **你点开播放的那条**：地址带 `m=<32 hex>`，请求量最大（实测 71～580 次分片请求）；
- **其余**：`m=` 为空字符串，靠 `encfilekey` 区分，信息流预加载的封面/下一条只请求 1～2 次。

早期版本只认 `m=`，其余整条丢弃——一次运行 1062 条媒体地址里有 1050 条因此没进队列，这正是"只下载了一个、之后的都不响应"的原因。现在的规则：

1. 有 `m=` 就用它当身份；
2. 没有就退到 `encfilekey`（同一条视频的所有分片共用），身份取 `ek` + `md5(encfilekey)`；
3. `ek` 身份要求被请求 **≥3 次**才开工，避免把信息流预加载的内容也下载下来；
4. 同一视频可能同时以两套身份出现（带 `m=` 的地址也带 `encfilekey`），所以每条记录同时保存两个身份，处理完一并标记，避免下两遍；
5. 这些分片请求的地址用**完整 GET**（不带 `Range`）拿得到整文件——实测 `206` 的地址 HEAD 回来是 `200` + 完整 `Content-Length` + `X-enclen: 131072`。

封面图/头像也走 `stodownload`，`capture.py` 会看响应头 `Content-Type`，非 `video/mp4`、非 `octet-stream` 的不记录（只看头，不碰 body，不影响流式透传）。

### 3.5 结构闸门：这份头到底是不是这条视频的

把"内存头 + 密文[enclen:]"当成一个虚拟文件视图，按顶层 box 走一遍，读到 `mdat` 就停（继续走会把填充字节当 box，实测能"读"出 3.9GB）：

- 首 box 必须是 `ftyp`；
- 必须出现 `moov`，且 **`moov` 的结束位置不能超过整个文件长度**——moov 比文件还大只可能是别人的头。实测 0.5MB 的密文配上 452 秒视频的头，声明总长只差 44KB，光看容差会放过它，最后写出一个 0.5MB / 452 秒的假文件；
- `mdat` 声明末尾与实际文件长度之差 ≤ `max(64KB, 0.5%)`。对的头差 0，错的头差 3MB～713MB。

`X-enclen` 取 HEAD 响应头；`< 1024` 或 `> 4MB` 就回退默认 131072（带 `Range` 的请求会把 `X-enclen` 回成本次范围长度，不能当依据）。

### 3.5 解码校验里哪些"错误"不算错

`ffmpeg -f null` 会对 B 帧的 DTS 顺序报 `non monotonically increasing dts to muxer in stream 0`，那是 **null muxer 的牢骚，不是文件损坏**。实测一条完好的 452 秒 / 13542 帧视频全片解码只有这 3 行，却因此被判"解码失败"，重试三次后放弃。现在 `non monotonically increasing dts` 与 `Application provided invalid` 两类消息不计入错误，只统计真正的读数据/解码错误。

下载侧还有一个同类陷阱：curl 拿到 `HTTP 200` 不等于收全，连接中途断开时 `exit=18` 会留下半截文件，必然拼不上头，所以 `curlExit != 0` 直接算本次失败、进入重试。

运行日志写在 `work\run.log`（自己追加，不用 `Start-Transcript`——实测那份日志真实运行时一直是 0 字节）。

## 4. 为什么要“先播放一次”

内存里只会保留**最近播放过**的视频头。没有播放过，就没有明文头可用——这也是当前唯一无法绕开的限制。批量下载需要额外的界面自动化。

## 5. 兼容性排查思路

如果哪天又失效了，按这个顺序查：

1. 代理是否真的被微信使用：看 `flows.log` 有没有 `finder.video.qq.com`；
2. 视频地址能否下载：`curl -I` 看 `X-enclen`；
3. 内存里是否还有 `ftyp+moov`：运行 `-SelfTest` 后手动用 `MemScan` 扫一遍；
4. 微信是否换了容器进程名：`Get-Process *WeChat*`。
